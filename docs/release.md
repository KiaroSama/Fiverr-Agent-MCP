# Release contract

Release only an experimental/prerelease while live account readiness is unverified. Public destination: KiaroSama/Fiverr-Agent-MCP. Original code GPL-3.0-or-later; adapted upstream notices remain separate.

Manual CI defaults to `validation_only:true` for native source/test/security/coverage validation. With `validation_only:false`, Windows additionally builds once, signs through the branch-restricted `windows-signing` environment, verifies the pinned owner certificate and PE content digest, checks tamper/wrong-signer rejection, packages and verifies the extracted signed executable. Only the signing step receives the two encrypted signing inputs; no private material enters distribution archives. Other native targets remain validation-only until their approved platform signing contracts exist. Green validation alone is not final package or installation evidence.

The established final distribution path, once signing prerequisites and their verification are implemented, must build the executable once per real target, package allowlisted public payload, generate dependency license texts and release file hashes, read archives back and execute extracted version/status/desktop-config from an unrelated CWD without developer tools. Native Windows ZIP, Unix tar.gz, one instruction plugin ZIP, exact source tar.gz, per-target SHA256SUMS and release JSON are required. Common source/plugin archives must match byte-for-byte across native targets.

The manual Release workflow delegates identity and asset checks to Rust xtask. It requires a successful manual CI run on the exact current default `feature/fiverr-native` SHA, all four native/security jobs and the Windows signed artifact. It downloads only that run's Windows/source/plugin assets, validates hashes/source/signing receipt, refuses an existing version tag and creates an experimental draft before publication. This migration does not itself dispatch or publish a release. A tag push does not automatically publish. No fabricated smoke output, coverage or signing claim. Final publication/activation requires the approved owner identity and genuine target-appropriate signing; hashes or provenance do not substitute for signing. The owner-authorized Windows certificate is self-signed/private, not publicly trusted; Windows/SmartScreen may still warn. The tracked public certificate and SHA256 pin identify the expected signer, not a public CA or reputation guarantee. No system trust-store change is performed. Apple Developer ID/notarization and other-platform final signing remain unresolved.

Publication validation requires the exact version-derived Windows native ZIP, source tar.gz and plugin ZIP names, with exactly one checksum entry for each. It binds the target/product/version/source identity, external and embedded release metadata, every native member hash and the signing receipt's executable hash before any GitHub release mutation. Companion archives must parse under the bounded archive policy and common plugin/source/native bytes must agree. This is integrity binding to the Windows CI attestation; Linux publication does not independently rerun Authenticode, and a receipt boolean alone is not cryptographic signature proof. Synthetic validator fixtures never publish a release.

Keep the exact source archive and scripts beside binary assets for GPL corresponding-source obligations. Do not ship private state/config/browser profiles/logs, local workspaces, tokens or user files. Source/plugin/native inclusion is explicit; blindly zipping the checkout is forbidden. Final reports must identify source SHA, run URLs, job conclusions, archive hashes and unresolved acceptance blockers.
